# 安全边界与限制（推送二次确认 MVP）

## 当前保证

- **保护范围以登记为准**：只有通过桌面端登记过的仓库会被拦截；未登记仓库回落到全局开关，该开关默认关闭，因此装完 GitGuard 不会自动拦截其它仓库的 push。GitGuard 不扫描磁盘、不自动为仓库安装 Hook。
- **记录丢失不放行**：桌面端安装 Hook 时把该次登记的仓库 id 写进脚本；CLI 带 id 但配置里找不到同 id 记录（配置被删除/回滚、仓库被复制）时按「记录丢失」处理，仍要求确认并提示重新登记，不回落成放行。仓库 id 只用来把脚本对回记录，缺少或不匹配只会让结果更严格。
- **fail-closed**：未知、非法或不可判断的情况一律返回非零退出码；只有显式 `Decision::Allow` 映射为 0。
- **确认是必要条件**：启用保护的仓库，CLI 必须在配置的超时内得到用户确认——终端通道需在 `/dev/tty` 上读到 `y`/`yes`，桌面端通道需收到与本次请求 `request_id` 一致的 `Confirmed`；连接失败、超时、响应非法、`request_id` 不匹配、EOF 与无法识别的输入都按拒绝处理。
- **一次性批准**：待确认请求以 `request_id` 为凭据，取出即消费；重复确认或 ID 不匹配返回 `no_pending_request`。同一时刻只保留一个请求，新请求会把旧请求按 `Cancelled` 结束。
- **推送只发生一次**：确认通过后 GitGuard 不执行任何 Git 命令，而是以退出码 0 放行，由原本的 `git push` 完成推送；不存在「Hook 与桌面端各推一次」的路径。
- **确认后再校验**：无论走终端通道还是桌面端通道，确认后都会重新校验每个 ref 仍指向请求中的 OID，并重新校验 ref 名与 OID 形状；不一致则以退出码 1 拒绝，远端不变。
- **Hook 不吞掉用户 Hook**：安装时若已存在外来 `pre-push`，先备份为 `pre-push.gitguard-backup`，脚本链式调用它；CLI 拒绝本次 push 时脚本立即以同一退出码结束，不会绕过确认去执行被备份的 Hook；若 Hook 被外部改动且备份已存在，安装直接拒绝；卸载时还原备份而不是删除用户的 Hook。
- **确认通道自动选择**：CLI 仅在 stdout/stderr 至少一个是终端且 `/dev/tty` 可打开时走终端确认，否则只走 IPC 桌面端确认；不能判断通道时按拒绝处理，绝不静默放行。
- **终端输出不可伪造**：终端界面渲染前过滤控制字符、ANSI 转义与 bidi 控制符，remote URL 中的用户名/密码替换为 `***`；颜色码只在过滤之后由 GitGuard 自己叠加，仓库内容无法借颜色码拼接转义序列；分页与配色只影响展示，不改变任何放行决定。
- **改写提示不改变结论**：非快进更新（`--force`、`--force-with-lease` 或 refspec 里的 `+`）在终端与桌面端标为历史改写，tag 更新一律按改写提示；祖先关系无法判断时（对象存在但不是 commit、Git 比对失败）也按改写提示。远端对象在本地缺失时提交列表本身就列不出，按既有 fail-closed 规则拒绝本次推送，不会展示标记。该标记只用于提醒，不参与退出码或放行判断。
- **本地传输最小权限**：IPC 使用 Unix Domain Socket，文件权限 `0600`；单条消息上限 64 KiB，读 5 分钟、写 30 秒超时，超时或非法 JSON 直接断开且不回包。
- **配置不被静默覆盖**：配置文件 JSON 损坏或 `schema_version` 不认识时返回错误，桌面端停止写盘。
- **无网络与无凭据处理**：不访问云端业务服务，不含遥测、自动同步或凭据存储；不记录 Token、私钥、完整环境变量或含密码的 URL；错误只写 `stderr`。
- **审计不削弱 fail-closed**：审计由 CLI 在推送进程内写入，写入或保留清理失败只往 `stderr` 加一行提示，退出码与推送结果不变；审计读不到、被删除或被篡改都不会被当成「已确认」或「已放行」。桌面端只读审计，不补写记录。
- **审计与诊断默认脱敏**：URL 中的用户名/密码与 `access_token` 类查询参数、`KEY=VALUE` 形式的 Token/密码/私钥、常见 Token 前缀段以及 PEM 私钥整段在写入前被替换；控制字符、ANSI 与 bidi 控制符被替换为空格，单字段截断到 512 字符。诊断摘要由 Rust 侧渲染，内容只有运行状态与最近事件，不含提交内容、环境变量或凭据；导出的文件权限为 `0600`，目标已存在时拒绝覆盖。
- **命令只返回稳定码**：桌面端命令只返回稳定错误码与 `HookStatus`，用户可见文案来自前端语言包。
- **文件夹选择只读**：前端只申请 `dialog:allow-open` 权限，对话框仅返回用户选中的路径，不列举、不读取目录内容；路径在 Rust 侧二次校验（必须是绝对路径且是目录）。
- **界面导航不构成控制**：侧边栏页面、设置快捷键（macOS `⌘,` / 其它平台 `Ctrl+,`）与原生菜单只负责切换视图；菜单里没有推送相关入口，前端仍无法通过界面、快捷键或菜单绕过 Hook 与 Rust 侧校验。
- **测试隔离**：真实 Git 集成测试只使用临时仓库与本地 bare remote，隔离 `GIT_CONFIG_GLOBAL` / `GIT_CONFIG_SYSTEM` 与 `HOME`，不触碰用户的日常仓库与全局配置。

## 已知削弱点（当前实现明确不抵御）

- **旧版 Hook 脚本**：本版本写出的脚本与 CLI 都不再识别 `GITGUARD_CONTROLLED_PUSH`，但升级前写入仓库的脚本仍含旧的跳过判断：命中该环境变量时它不调用 CLI 就直接放行。重新添加该仓库（重写 Hook 脚本）后才会消失；在此之前，能设置环境变量的本机用户仍可跳过确认。防护目标是「防误推」，不是「防本机恶意用户」。
- **不带仓库 id 的脚本没有记录丢失检测**：旧版或外部写出的 Hook 脚本不带 `--repository-id`，CLI 只能按仓库路径查配置；记录不存在时回落到全局开关（默认关闭，即放行）。重新添加该仓库会重写脚本并写入仓库 id。
- IPC 没有身份认证或请求签名，只依赖 socket 文件权限（`0600`）；本机同一用户下的其它进程可以连接并伪造请求。
- 桌面端不校验请求来自哪个 Git 仓库进程，只按 `repository_path` 读取提交列表。

## 明确不属于当前保证

- 本机管理员可以删除、替换或绕过 Hook；GitGuard 不声称抵御拥有完整本机控制权的用户。
- 尚无 Hook 升级与版本漂移检测：健康检查只判断 GitGuard 标记整行是否存在，不校验脚本正文、也不记录版本；标记仍在的旧脚本或篡改过的脚本都会被判为 `Healthy`，也不会被自动升级。
- 尚未验证多 push URL、`pushurl`、URL rewrite、直接 URL、`core.hooksPath` 指向共享目录等边界。
- 尚无 Windows 实现（IPC 需要命名管道，Hook 脚本依赖 POSIX shell）；Windows 上的集成测试会被跳过。
- 尚无系统凭据库。
- 审计文件（`audit.jsonl`）是本机普通文件，权限 `0600`，但同一用户下的其它进程可以改写、删除或伪造事件；它不是防篡改凭证，也不能用审计缺失来推断「没有发生过推送」。审计目前只记录推送确认事件，不记录配置变更、Hook 安装/卸载或身份变更。
- 脱敏是模式匹配：非常规编码（如拆分拼接、base64 包裹的凭据）可能漏过；审计与诊断输出不应被当作可以公开分享的通用日志，分享前仍需人工确认。
- 终端确认依赖 `/dev/tty` 的可用性与所有权：同一控制终端上的其它进程仍可向终端写入内容，也无法阻止用户误输入。
- 图形客户端不会展示 Hook 的内容，用户只能依靠桌面端窗口确认；若用户在客户端里直接取消或关闭，推送会以 Hook 失败告终。
- 尚未验证桌面端崩溃、系统休眠、多仓库并发推送等异常时序。
- 前端展示与按钮状态不构成安全控制：即使绕过界面直接调用命令，最终仍由 Rust 侧校验与 Hook 退出码决定。
- 改写标记是客户端基于本地对象祖先关系的推断：不能区分 `--force` 与普通分叉推送，也不构成服务端证据；它只在可以列出提交时出现，远端是否接受推送仍由 Git 与服务端决定。
